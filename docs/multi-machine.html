多机协作：每台机器在干什么，为什么不会冲突

这份页面解释当前抓取任务的机器分工与防冲突机制。全组任何人看完都应该能回答两个问题： 「我这台机器该干什么」和「会不会和别人抢到同一条任务」。

一句话答案：没有分工表——所有机器都是对等的劳动力，任务靠原子抢占从共享队列里领，抢到了才算你的。

01角色：谁在干活

系统里只有四类角色，且除了「云库」之外都是可替代的——任何一台笔记本都能顶上另一个角色的活。

中枢云数据库
腾讯云上的一台服务器（Docker 里的 PostgreSQL，端口 15432）。它不是计算节点，只负责存三样东西：任务队列、配额账本、RAWG 密钥池。
不可替代 · 所有机器都要连它
劳动力worker 机器 × N
每台同学的笔记本。跑 uv run python -m cleaning.worker，反复「抢任务 → 抓数据 → 写库」。彼此完全对等，没有主从、没有分组、没有谁负责哪个 appid 段。
可替代 · 加机器 = 线性加速
观察窗状态面板
任意一台机器跑 uv run python -m dashboard.app。看队列进度、查单个游戏、按任务方式补抓。只读 + 补抓，不参与批量抓取。
可选 · 谁开都行
一次性seed 种子
枚举全量游戏、物化任务队列。全项目只跑一次（已完成），由组长执行。它不抓逐款数据，只把「有哪些游戏、每个游戏要抓哪些源」写进队列。
已执行 · 不需要重复
为什么没有「A 机器抓 appid 1-10000，B 机器抓 10001-20000」这种分工？ 因为分片会带来三个问题：分片边界要人工维护、机器快慢不均导致有的闲着有的堆积、某台机器下线时它的分片没人接手。 共享队列天然解决这三件事——快机器自然多做，慢机器少做，下线的机器留下的任务立刻被别人抢走。

02任务不是分配，是抢：一条 SQL 决定归属

每台 worker 启动后就进入循环：向云库要一批任务（默认 20 条），拿到就干，干完再要。 「要任务」这一步是用一条 SQL 完成的——它同时做两件事：挑出可做的任务 和 写上「这几条归我」的租约。 两步合一，中间没有缝隙，所以不存在「两台机器都以为任务归自己」的窗口。 

-- 简化示意（真实语句见 cleaning/worker.py 的 CLAIM_TASKS）
UPDATE fetch_tasks SET claimed_by = '我这台机器', lease_until = now() + '5 分钟'
WHERE (appid, source) IN (
    SELECT appid, source FROM fetch_tasks
    WHERE status = 'pending' AND 租约已过期
    ORDER BY appid LIMIT 20
    FOR UPDATE SKIP LOCKED   -- 关键：锁住的行别人直接跳过，不排队等待
)
RETURNING appid, source;

「不排队」很重要。 如果换成普通的行锁（FOR UPDATE 不带 SKIP LOCKED）， B 会停下来等 A 处理完才继续——机器越多、等得越久，最后比单机还慢。 SKIP LOCKED 让 B 直接跳过、去拿别的活，两台机器永远并行。

03五道防冲突机制

上面那条 SQL 解决了「抢」，但完整的不冲突还需要另外四层保障。每一层单独失效都不会造成脏数据。

机制解决什么问题失效时会怎样
原子抢占
一条 SQL + 行锁		 两台机器同时抢同一批任务 不可能失效：数据库行锁是硬保证。抢到的行会立刻写上 claimed_by
租约（默认 5 分钟）
claimed_by / lease_until		 机器崩溃、断网、强杀进程后，任务永久卡在「有人拿着」 到期自动回到可抢状态。不需要任何人工清理僵尸任务——这是刻意设计的，因为学生机器随时会合盖休眠
任务粒度 = 游戏 × 数据源
不是整款游戏		 「一个游戏的数据被两台机器各抓一半」这种担心 这是允许发生且无害的：每个源独立写入、各自幂等，谁抓哪几个源都不影响最终数据（详见下节）
幂等写入
INSERT ... ON CONFLICT DO UPDATE		 租约到期被重抢、同一份数据被抓两次 后写的覆盖先写的，结果完全一致。代价只是几次多余的请求
终态不再重跑
ok / empty / skipped		 已完成的任务被反复抓 三种终态的任务不会再进入可抢集合。只有 pending 和 error（退避到期后）才可能被抢

04那条最容易被误解的规则：任务粒度

队列里的「一条任务」= 一个游戏的一个数据源（例如「Hollow Knight 的 SteamSpy 数据」）。 一款游戏有 5~6 条任务（appdetails 中英文 / 全局成就率 / 社区成就页 / SteamSpy / 可能还有 RAWG）。 抢占的排序是先按 appid、同游戏内再按源码优先级，所以同一款游戏的几条任务通常会落在同一批、由同一台机器处理完。

情况会发生吗后果
同一款游戏的 6 条任务被两台机器分别处理 可能（批次边界处） 无害。各源独立写入，最终数据与单机跑完全一致
两条机器抓到同一条任务（同游戏同源） 正常情况不会 只在租约到期后被重抢时发生，幂等写入兜底，代价是白花一次请求
两台机器同时改同一行数据库 不会冲突 PostgreSQL 行锁串行化写入；后提交的赢。所有写入都是「整行覆盖」，不存在字段互相覆盖的中间态
两台机器同时执行 db init（DDL） 要避免 会争排他锁、可能堵住整个队列。建表只由一个人执行一次，其余人永远只跑 worker
实操建议：worker 随便开多少台都安全；但「改表结构」「重跑 seed」这类动作要协调—— 不是因为有数据冲突风险，而是它们会短暂锁表，让正在跑的 worker 空等。

05什么共享、什么不共享

资源在哪是否跨机器共享说明
任务队列云库 fetch_tasks共享抢占就是围绕它设计的
抓取历史云库 ingest_log共享不可变审计：谁在什么时候抓了什么，增删改都留痕
配额账本云库 api_usage共享所有机器发出的真实请求都记在同一个账本上
RAWG 密钥池云库 rawg_keys共享见下节——这是唯一「必须共享」的资源
限速器各机器内存不共享按域名分桶的 1 秒间隔是进程内的：N 台机器对同一站点就是 N 倍速率
抓取数据本身云库各源表共享没有本地缓存（已废除）：数据库是唯一事实源，机器换一台接着跑即可
.env 配置各机器本地不共享数据库地址相同，Steam key 可共用；不入 git

06唯二的全局约束

① RAWG：配额绑定 API key，不是机器必须共享

RAWG 免费档每 key 20,000 次/月。如果各机器各用自己的 key 且互不知情，就会出现 「5 台机器都以为额度是满的、结果一起超额」。所以 key 全部注册进云库的密钥池： 每次真实请求前原子地取一个「本月还有余额」的 key 并计数，所有机器看到同一份余额。 加机器对 RAWG 没有任何加速作用，扩容只能加 key。

② SteamSpy：只有按机器的速率限制不共享

SteamSpy 官方只公布 1 请求/秒，没有配额。我们取消了自设的每日上限， 只保留每台机器 1 秒间隔——这意味着 N 台机器对 SteamSpy 的聚合速率是 N 请求/秒。 这是刻意选择（否则 4.9 万个任务要跑 49 天），代价是机器开很多时要留意对方是否开始限流。
