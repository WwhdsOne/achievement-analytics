# 面板资源拆分与推荐服务内存实测

后续实现与验收已完成，见 [Rust 与持久化交付结果](../result/ZZY/rust-recommendation/RESULTS.md)。以下保留实施前的评估与 Python 基线记录。

日期：2026-10-20。范围：核对当前工作区的打包方式、在本机 Docker 实跑现有 Python 推荐服务、给出拆分与迁移方案。本次没有修改线上服务、部署流程或推荐算法，没有提交或推送。

## 结论

面板适合把研究成果数据和附件拆到服务器持久目录，后续按内容摘要增量上传。主面板 HTML 本身很小，主要增量来自 LYX 整包；单纯把 JSON 从 HTML 搬到另一个仍然嵌入二进制的文件，不能解决部署反复传输。

Python 推荐服务的内存确实较高：两次本机实跑，空闲工作集约 **1.41–1.43 GiB**，4 并发推荐峰值约 **1.70–1.73 GiB**。值得做 Rust 运行时对照，但当前没有 Rust 实测，不能承诺节省比例。优先迁移在线搜索、排序和解释，继续沿用已有冻结数据与 Python 数据准备流程。

## 一、面板体积从哪里来

按当前 `dashboard/main.go` 的实际 embed 清单计算，包含 `all:lyx` 的递归文件；以下 MB 均为十进制。

| 内容 | 大小 | 含义 |
|---|---:|---|
| 主面板 `dashboard/index.html` | 43,709 字节，约 43.7 KB | 并非当前主要体积来源 |
| 全部内嵌文件，85 份 | 19.75 MB | 目前随二进制一起发布 |
| 其中 LYX 成果目录 | 17.88 MB | 内嵌内容约 91% 来自这里 |
| 其中 LYX `WEB/index.html` | 5.33 MB | 其中 `lyx-data` 内联 JSON 为 5.22 MB |
| 研究图片 `figures/` | 1.63 MB | 适合独立持久化 |
| 根层 UI、脚本、样式与小型汇总等 | 0.24 MB | 可继续内嵌 |
| 固定 `analysis-report.json` | 1.49 MB | 未内嵌，但当前每次部署仍重复上传 |

检查时现有 `dashboard/build/achievement-dashboard` 为 31.47 MB，`upload.tar.gz` 为 14.17 MB。这是本地已有构建产物的大小，不能当成拆分后的实测收益；真正收益需拆分后用相同编译参数重新比较。

### 推荐做法：服务器持久目录 + 增量同步

- 小型 HTML / JS / CSS 继续随 Go 发布；LYX 完整目录、研究图片和冻结报告放 `/opt/achievement-dashboard/content/`，以只读挂载供 Go 提供文件服务。scratch 镜像可保留。
- 保持现有 URL 和 LYX 相对目录结构。原页还会跳转文档、图片和来源明细，不能只迁移一个 HTML 文件。
- 将“程序部署”和“成果同步”分开。首次同步完整资源；以后比较 SHA-256 清单，只上传变化文件。旧固定报告也按摘要跳过，不能因为普通程序更新而重传。
- 更新内容先写新版本目录，全部摘要验证通过再切换版本；保留上一版便于回退。普通部署不删除持久数据，资源缺失时报明确错误。
- 保留成果版本和来源摘要，确保新程序对应正确数据。首次部署与内容同步失败时，都不能静默展示错误版本。

这样普通改代码不再重复传约 19.5 MB 的 LYX 与图片原始内容；上传压缩包能缩小多少须重建测量，不能直接拿原始文件大小相减。

### LYX 内联 JSON 是否还需要拆

可以再把 5.22 MB 的 `lyx-data` 提取为独立 JSON，由页面加载，并配置 ETag / Last-Modified 和合理缓存。这样只更新交互脚本时，浏览器也能复用未变的数据。需要调整成果同步脚本与页面加载失败提示，并核对原数据摘要和交互结果。

这是第二层优化：第一层解决**部署时反复上传**，第二层解决**浏览器反复下载**。只把整页放到服务器，首次打开仍然需要下载页面里的数据。

其余选择：继续全量内嵌最简单，但每次发布都带全部内容；迁到对象存储也可行，但当前规模会增加域名、跨域和部署配置。本项目优先使用已有服务器持久目录。

## 二、Python 推荐服务实测

### 条件与口径

- 本机 ARM64、Docker Desktop Linux 引擎 29.6.1；Docker VM 内存上限约 7.75 GiB。
- 使用当前最小部署包构建 `achievement-recommendation:memory-bench`，不是研究用全套 Python 环境。镜像 ID：`sha256:f1ea793e4e2d88504fe1c457ed6be649e22283b0d4e0cec59bf327b06ef1c509`。
- 被测容器限制 1 CPU、4 GiB 内存、无额外 swap；本机端口 18605。仅挂载已有缓存，挂载与容器根文件系统都只读；不传数据库或 AI 凭据，不调用点评。
- 快照 `recommendation-v1-c58f1d57439d2c28`；图谱 `kg-v1-99ed019b805815a32e2414cb09007475b11c2adaf39c5d488fbdc571c8ba78e5`；41,279 款候选。
- 第二轮 `/api/meta` 明确返回 `source=persistent_cache`、`cache_reused=true`、`database_access=false`，启动指针摘要前后不变。
- 在容器外每 0.5 秒采样，工作集按 Docker Linux CLI 口径计算：cgroup usage 减 inactive_file；另记录原始 cgroup 用量、PID 1 RSS 和进程高水位。辅助读取进程不进入业务阶段汇总。[Docker 内存统计说明](https://docs.docker.com/reference/cli/docker/container/stats/)

### 结果

以下为第二轮完整记录；GiB = 1024³ 字节。

| 状态 | Docker 工作集 | 备注 |
|---|---:|---|
| 启动完成后空闲 | 中位数 1.405 GiB | 空闲采样 10 秒 |
| 6 次串行推荐 | 采样峰值 1.477 GiB | 单种子、组合种子、年份筛选 |
| 4 并发，共 8 次推荐 | 采样峰值 1.699 GiB | 真实推荐与解释响应 |
| 请求结束后空闲 | 中位数 1.541 GiB | 再空闲采样 10 秒 |

PID 1 启动后 RSS 为 1.419 GiB，整个测量期进程高水位为 1.713 GiB，请求结束后 RSS 为 1.555 GiB。未扣文件缓存的 cgroup 用量采样峰值为 2.201 GiB，不能与工作集混为一个指标。

从容器启动到接口就绪约 21.2 秒。6 次串行推荐耗时约 0.65–1.55 秒；4 并发时单请求约 0.74–6.24 秒。另有 3 次真实中文搜索。14 次推荐全部返回 5 个结果；重复查询在串行与并发下响应摘要一致。第一轮启动约 22.2 秒、空闲工作集中位数约 1.434 GiB、4 并发峰值约 1.725 GiB，量级一致。

Docker 当前分别显示镜像 **DISK USAGE 385 MB** 与 **CONTENT SIZE 88.6 MB**（inspect Size 为 88,563,387 字节）。这两者都是镜像存储口径，均不是运行内存，也不能当成当前部署脚本的上传量；部署脚本当前上传小型源码包，在服务器构建镜像。本次仅打包的源码压缩包约 124 KiB。

局限：这是本机 ARM64、已有持久缓存条件下的结果，服务器是 AMD64，不能直接推断线上响应耗时；4 并发只是一次小规模负载检查。采样峰值可能漏掉更短的瞬时尖峰。镜像大小也不含挂载的约 800 MB 活跃图谱与快照。

### 复现与记录

先构建现有最小部署包镜像，再运行：

```bash
uv run --project result/ZZY/deploy --frozen python result/ZZY/deploy/benchmark_memory.py
```

脚本拒绝远端 Docker 和覆盖同名容器，最后仅移除本次创建的测试容器；镜像保留。要求已有 `result/ZZY/runtime/dashboard/latest-startup.json` 及对应快照。本次完整第二轮数值保存在被 Git 忽略的 `result/ZZY/build/deploy/python-memory-benchmark-20261020.json`；脚本通过 `RESULT_JSON=` 输出结果，不写原始游戏数据。

## 三、Rust 值不值得做

值得做一个保持结果一致的运行时替代。当前代码既保留游戏记录、实体与边偏移，又建立每游戏关系集合、倒排集合；服务还初始化基线查询索引。源码上存在多套索引共存，但这次没有分别测量各对象占比，不能把某一套直接认定为全部内存来源。

三种路径的取舍：

| 路径 | 优点 | 代价与边界 |
|---|---|---|
| 先精简 Python 初始化与重复索引 | 改动较小，可建立额外对照 | Python 对象开销仍在，节省量待测 |
| **Rust 在线服务，Python 继续准备数据** | 可用整数 ID、紧凑数组、共享只读索引，缩小运行依赖 | 需要逐项验证排名与解释；推荐先做这一范围 |
| Python 数据准备和在线服务全部重写 | 统一技术栈 | 数据库提取、图谱生成、绑定校验也要迁移，范围大 |

建议第一版 Rust 保持 Go 面板正在代理的 meta / search / recommend 接口，直接读现有快照与图谱。不要把约 758 MB 的关系 JSON 一次性解码并长期保存成通用 JSON 对象；可流式建立紧凑索引，解释明细按需读，并限制并发临时工作区。持久缓存继续放服务器，普通代码发布不重传、不刷新数据库。

对照必须固定数据版本、41,279 候选及现有权重：标签 / 类型 / 开发商 / 发行商为 0.75 / 0.15 / 0.10 / 0；保留关系内 IDF-Jaccard、联合种子等权、年份先筛后排、缺失关系不重新归一化等规则。核对中文搜索、过滤、并列排序、分数、贡献总和与事实路径，避免内存变小却改变推荐含义。

在同一架构、同一 CPU/内存限制下，与当前 Python 基线比较镜像、启动时间、空闲 RSS、并发峰值和延迟，再决定替换。**目前只有 Python 实测，没有 Rust 节省比例。**
