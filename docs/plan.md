# 项目计划：分析用户和玩家更愿意玩什么样的游戏

> **总目标**：用户和玩家更愿意玩什么样的游戏？
>
> "愿意玩"用参与度指标操作化——游玩时长、成就完成深度、活跃度、全成就比例。参与度高的游戏 = 玩家"更愿意玩"的游戏。

## 研究主线

| # | 定位 | 问题 | 方法 |
|---|------|------|------|
| Q1 | 支撑 | 成就难度与玩家能力如何刻画？ | IRT 2PL（难度 b、区分度 a、能力 θ），全局完成率作 b 的代理交叉验证 |
| Q2 | 核心 | 哪些游戏特征让玩家更愿意玩？ | 特征回归 + SHAP 归因，特征含类型 / 价格 / 标签 / 热度 / 难度结构 |

Q1 产出难度结构特征喂给 Q2（太难劝退、太简单无聊，难度是解释偏好的关键变量）；Q2 直接回答总目标。

## 数据源（Steam 单一生态）

| 来源 | 关键字段 | 用途 |
|------|---------|------|
| `GetOwnedGames` | 游戏库、playtime_forever、rtime_last_played | 参与度（时长聚合） |
| `GetPlayerAchievements` | 成就解锁状态、unlocktime（天级） | Q1 响应矩阵、完成深度 |
| `GetGlobalAchievementPercentagesForApp` | `name`（内部名）+ `percent` | **Q1 核心**：percent 作难度 b 代理 |
| `appdetails` | 游戏元数据（类型 / 价格 / 成就总数）；批量已失效（400），单 appid 请求 | Q2 特征 |
| `GetSchemaForGame`（需 key） | 成就架构 `name`→`displayName`（完整列表） | **名称映射的唯一来源**（appdetails 仅 10 个 highlighted 展示名） |
| SteamSpy | owners 估算、标签、CCU | Q2 特征补充 |

## 清洗核心步骤：成就名称映射

两个接口的 `name` 都是 **API 内部名称**（如 `ACH41`），显示名称在 `GetSchemaForGame` 的 `displayName`（如 `The Dark Soul`）。以内部名称为键 JOIN schema 与全局完成率，为每款游戏生成**标准成就数据文件**：

```json
{"api_name": "ACH41", "display_name": "The Dark Soul", "percent": "93.9"}
```

要点：关联键用 `name` 不是 `displayName`；映射输出差集报告（DLC / 隐藏成就等单侧项不静默丢弃）；**`GetSchemaForGame` 需 API key，key 是映射 pipeline 的硬依赖**；建模只消费映射后的标准文件。

## 数据规范

- 分层：`raw/`（只读）→ `interim/` → `processed/`（建模输入）
- 原始数据不入 git，玩家 ID 进 processed 前哈希化
- 全局完成率 percent 随抓取批次漂移，建模绑定固定版本
- API key 放 `.env`，读取走 `crawler/config.py`

## 爬虫规范（硬性）

- 限速 ≥ 1s，公开数据，遵守 robots / ToS
- 缓存 + 断点续爬，重试 ≤ 3 次，失败入日志
- appdetails 优先批量查询省配额
- 不爬需登录态页面

## 探索性分析与 baseline

描述性分析：拥有游戏数、时长、成就数、全局完成率、类型标签分布、长尾与选择偏差。

baseline（高级模型前必须有）：
- Q1：原始全局完成率（logit）直接作难度 + Rasch/1PL
- Q2：线性回归 / 单特征相关 + 散点拟合

## Q1：IRT 难度建模（支撑）

1. 建模单位：玩家×成就，区分未观测 / 未拥有 / 未解锁 / 失败；DLC 单独建模
2. 2PL 估计难度 b、区分度 a、能力 θ
3. 全局完成率三种用法对比：外部代理 / 贝叶斯先验 / 对照特征
4. 检查：收敛、极端值、稀疏性、异常玩家影响
5. **输出游戏难度结构特征**（供 Q2 消费）：难度分位数、极难成就占比、平均区分度
6. 一致性检验：IRT 难度 vs 全局完成率，分析分歧样本

## Q2：偏好回归 + SHAP 归因（核心）

### 因变量：参与度操作化

- 平均成就完成率（中位 / 加权）
- 首末成就完成率落差（"入坑深 / 弃得快"）
- 平均游玩时长 / 中位时长（GetOwnedGames 聚合）
- 全成就达成比例
- CCU / owners 比值（活跃度代理）

多指标做相关性检查，避免重复编码。

### 特征工程

- 类型 genres、SteamSpy 标签（低频合并）、价格、热度（owners log、CCU）
- **难度结构特征**（来自 Q1）：成就总数、P10 完成率、极难成就占比、IRT 难度聚合
- 发售年份（控制年代效应）
- 多重共线性检查

### 建模

- baseline：线性回归
- 主线：XGBoost / LightGBM
- 归因：SHAP summary + dependence plot
- 评估：按发售年份 / 类型分组交叉验证，R² / RMSE

### 稳健性

- SHAP 是模型归因非因果，报告措辞区分
- 分组检验（独立游戏 vs 3A）
- 多个参与度定义分别建模，检验特征排序稳定性
- 样本量 vs 特征维度比，防过拟合

## 风险与局限（必须讨论）

**数据风险**：API 配额（缓存 + 批量）、档案公开率低（样本按公开率放大）、游戏样本不足（Q2 样本单位是游戏）、成就架构不一致（差集报告）。

**建模风险**：IRT 不收敛（退回 Rasch/1PL，Q2 难度特征降级用全局完成率统计量）、Q2 过拟合（baseline 对照 + 正则化 + CV）。

**局限**：公开档案选择偏差（结论偏核心玩家口味）、unlocktime 天级精度、全局完成率漂移、分母是"曾启动账号"非"购买者"、SteamSpy owners 估算、"愿意玩"是代理变量、SHAP 非因果、观察性数据无因果、反作弊误伤速通玩家。
