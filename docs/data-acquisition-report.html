02 / 目标与边界

玩家更愿意玩什么样的游戏？

先确定问题与观察单位，再决定抓什么，避免先收集大量用不到的数据。

把“愿意玩”拆成可观察的参与信号：
玩多久、完成多深、是否仍然活跃。

本阶段收集的两侧信息

  • 游戏是什么样类型、价格、发售年代、玩家标签、成就体系。
  • 人群参与到什么程度全局成就完成率、同时在线人数、拥有量估算及补充时长。

明确限制研究范围

  • 仅纳入2026年前发售的游戏排除当年新作，减轻上市初期数据（尤其是大批AI游戏）尚未稳定的影响。

这些是游戏级人群数据，不能直接代表某个玩家的偏好，也不能把关联写成原因。

口径依据：README、AGENTS.md与阶段报告。全局完成率不是个人通关记录。

04 / 数据源选择

不同来源，补齐不同信息

Steam提供官方身份与成就，SteamSpy补充玩家标签与热度，RAWG提供时长、评分与玩家状态。

来源 拿到什么 解决什么问题 接入方式
Steam 商店搜索 + 中英文详情 游戏列表、名称、类型、价格、发售日 定义研究范围，建立统一游戏身份 公开入口当前流程免key
Steam 成就全局接口 + 社区页 完成率、展示名称、成就描述 把数值完成率与人能看懂的名称对齐 公开入口两源共同校验

RAWG 时长、评分、通关与弃坑等状态计数 补充Steam公开聚合数据的缺口 需要key共享配额账本

05 / 抓取到入库

数据怎样变成可用的表？

用一条可恢复的流水线完成枚举、排队、抓取、校验和入库，原始记录保存在PostgreSQL。

01

全量枚举

商店搜索筛选带成就游戏，再按发售年份确定研究帧。

02

展开任务

一条任务 = 一款游戏 × 一个数据源。RAWG按评价门槛安排。

03

按缺口抓取

worker领取未完成任务，按来源限速；失败退避或挂起。

04

映射与校验

完成率与展示名称对齐，异常进入台账，不静默忽略。

05

分源入库

各源独立写表，重复写入不产生重复记录，保留真实抓取时间。

06

复核与收尾

看队列、修映射、复核终态，再整理阶段规模与质量报告。

共同关联键：Steam AppID

同一游戏的商店、成就、标签与补充信息可联合查询。

任务表回答：还该抓谁？

fetch_tasks保存当前状态、尝试次数和租约，支撑续跑。

审计表回答：何时抓过？

ingest_log保存历史；请求账本单独记录实际请求消耗。

流程依据：cleaning/schema.sql、seed.py、worker.py、writers.py。采集原始事实不依赖本地文件缓存。
06 / 初步描述性成果

已经可以描述成就体系的规模与分布

固定快照共50,922款：50,705款有成就统计，50,881款有官方类型，41,281款带玩家标签。与原始研究帧不同，不混用分母。

这说明游戏的成就体系与完成深度存在差异；还不能据此断言“更难所以弃坑”。

图表仅从2026-10-01固定快照聚合，无预测结果。低完成率还可能受内容类型、隐藏条件、玩家基数和发行时间影响；类型与标签均为游戏级计数，不代表受欢迎程度或映射准确率。
