## 1. 范围与口径

**为什么是这个范围**：研究问题需要「游戏特征 × 参与度」，因此要求游戏①有成就体系（成就完成率是难度与参与度的载体）②有足够的玩家基数（否则统计噪声大）。最终口径为：

- **带 Steam 成就的游戏**（商店搜索 `category2=22` 过滤），全站约 8.2 万款
- **仅 2026 年以前发售**：排除当季新作（评价数/完成率尚不稳定），得到 **50,956 款**

**明确了不做什么**（避免范围蔓延）：不做逐玩家档案抓取。项目只需游戏级聚合量（全局完成率、拥有量、时长），这既满足研究问题，也把抓取量从「玩家数 × 游戏数」降到「游戏数」量级。

## 3. 管道设计（要点）

抓取采用 **gap 驱动的共享任务队列**：队列（`fetch_tasks`）在共享 Postgres 里，任何一台机器都能抢占任务；没有分工表，也没有中心调度器。

- **原子抢占**：一条 `UPDATE … WHERE (appid, source) IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING` 同时完成「选任务」与「写租约」，多机不会重复抓同一条
- **`SKIP LOCKED`**：别人锁着的行直接跳过而不排队，因此加机器能线性提速
- **租约 5 分钟**：机器崩溃/休眠后任务自动回到队列，无需人工清理
- **幂等写入**：全部 `INSERT … ON CONFLICT DO UPDATE`，重复抓取不产生脏数据
- **终态收敛**：`ok / empty / skipped / exhausted` 是终态，不再重跑，队列单调收敛

机制讲解（含抢占示意与「为什么不会冲突」）见 `docs/multi-machine.html`。

## 5. 数据质量：发现并修复的问题

这一阶段的价值不止于「抓到数据」——**抓取过程中发现并修复了 8 类问题**，其中 3 类曾造成实际数据损失。全部修复都有对应测试（当前测试套件 123 条全过）。

| # | 问题 | 根因 | 修复 | 损失与恢复 |
|---|---|---|---|---|
| 1 | 成就名映射台账出现 37 条「不一致」 | 用**精确浮点**比对两源 percent，把 ≤0.1 的舍入差误判为顺序错位 | 改为**逐位容差判定**（≤0.5pp）+ 台账记录 + `repair_mapping` 收尾工具 | 假阳性 37 条，复核后确认本来就正确 |
| 2 | 社区成就页抓取白白重试 3 次 | Steam 对改过名的老游戏 302 重定向（如 appid 300 → DOD:S），httpx 默认不跟随 | 开启 `follow_redirects` | 无数据损失，省下重复请求 |
| 3 | worker 崩溃：**数据库死锁** | 多机各自按**不同顺序** upsert 同一批 `api_usage` 记账行，行锁成环 | ① 记账移出任务事务；② **按 source 排序**写入；③ 死锁自动重试（40P01/40001） | 顺带修掉「先清零再写库」导致的**丢账** |
| 4 | RAWG 任务被静默判为 `skipped` | 凭据判据 `rawg_enabled()` **只看本地 `.env`**，不知道共享密钥池 | 新增 `key_available()`（认池子），删除该 footgun 函数 | 误伤 2 条；若带病全量跑会烧掉 11,706 条 |
| 5 | SteamSpy 间歇 403 把任务烧成 `exhausted` | Cloudflare 挑战被当成普通失败，3 次快速重试耗尽重试预算 | 识别挑战 → 抛 `SourceUnavailable` → **任务放回 pending、源级挂起** | 已烧 23 条，全部重置回收 |
| 6 | **7,402 条 appdetails 被误判「无数据」**（最大一次） | 429 限流 → 请求失败被 `fetch_appdetails` **吞成「跳过」** → 上层看到「没数据」→ 落**终态 empty** | ① 失败一律上抛（可重试的 error）；② 429 尊重 `Retry-After` 等待重试，仍 429 则挂起源；③ 软拒绝重试 3 次再判空；④ 新增终态复核工具 | 重置后重抓 **7,372/7,374 恢复**（99.97%），最终 empty 仅 2 条 |
| 7 | DDL 把整条管道堵死 | `db init` 的排他锁被滞留连接挡住后**排队**，后续所有请求（含抢任务）一起堵 | 约定「建表只由一人执行一次」+ 排查手册（`pg_stat_activity` 找 `idle in transaction`） | 管道停摆约 5 分钟，无数据损失 |
| 8 | 前端面板不显示 / worker 静默失效 | 重复声明 `const` 导致整段 JS 语法错误；容器 `id` 丢失 | 交付前 `node --check`；补 id | 工具问题，无数据影响 |

**贯穿性教训（三次踩同一类坑）**：`skipped`（问题 4）、`exhausted`（问题 5）、`empty`（问题 6）都是**终态**，一旦判错就永久丢数据。因此确立两条硬规则：

1. **请求失败 ≠ 没有数据**：抓取层要么拿到数据、要么抛异常；禁止「失败 → 返回空 → 上层记 empty」
2. **终态必须可复核**：`uv run python -m cleaning.requeue_empty --status empty,exhausted --apply` 可把终态任务放回队列重验（本次靠它救回 14,973 条）

## 6. 已知局限（报告与展示必须声明）

### 6.1 RAWG 覆盖率有限（**本阶段最大的口径限制**）

| 事实 | 数值 |
|---|---|
| RAWG 任务只建给「评价数 ≥ 100」的游戏 | 16,562 款（占全量 32.5%） |
| 其中成功匹配 | 15,770 款（匹配率 **95.2%**） |
| **对全量游戏的覆盖率** | **30.9%**（15,770 / 50,956） |
| 未匹配 | 756 款（占 RAWG 任务 4.6%） |

未匹配的两类原因（抽样 8 款逐一手工重验，0 命中）：

1. **RAWG 确实没有**：小众独立游戏、日文视觉小说、名字过于通用的作品（如 `VHS`、`The Red Button`）
2. **候选校验上限放弃**：匹配算法为避免配额失控，最多校验 6 个候选；名字通用的游戏会在此处**提前放弃**（抽样中 5/8 属于此类）。这属于「不确定」而非「确定没有」，当时的实现未区分二者

**影响**：凡使用 RAWG 字段（metacritic、评分、平均时长、玩家状态分布/弃坑率）的分析，其样本只能限定在这 15,770 款内，且**偏向评价数高的主流游戏**。报告中必须写明，不能用它推断全量市场。

**决策**：本阶段**不做**高上限重验（需再花约 1.5 万次配额），而是把该局限写入口径说明。

### 6.2 只有游戏级聚合，没有个体玩家

所有「玩家行为」都是人群聚合量（全局完成率、拥有量区间），**不能推断个体偏好**。Q2 的「偏好」是从人群参与度反推的，措辞不得越界。

### 6.3 其余口径说明

| 项 | 说明 |
|---|---|
| 全局完成率会漂移 | 随抓取批次缓慢变化，建模必须绑定 `dataset_versions` 登记的数据版本 |
| `steamspy.owners` 是区间估算 | 只能作数量级参考，不能当精确销量 |
| `steamspy.average_forever` / `median_forever` | 已失效恒为 0（上游问题），时长分析改用 RAWG 的 `playtime` |
| 成就名映射 | 判定用逐位容差（≤0.5pp）；**未解决 3 条**（appid 627690 / 767490 / 1851090），建模时过滤 `resolved=false` |
| `empty` 的语义 | 多数为「该游戏确实没有该数据」，但历史上有假空（问题 6）；本次已全量复核过 |
| RAWG 使用条款 | 免费档限非商业用途，且**要求使用数据的页面加 RAWG 回链**——最终报告/展示页必须落实 |

## 7. 结论与下一步

**结论**：数据获取阶段完成。核心的成就数据（197 万条、50,738 款）覆盖完整且名称映射 100% 可用；六个源的字段足以支撑 Q1（难度结构）与 Q2（偏好归因）。主要代价与局限已在 §6 明确。

**收尾动作（进入建模前必须做）**：

1. **登记数据版本**：`dataset_versions` 当前为空——按项目规范，建模必须绑定固定版本（percent 会漂移）
2. **处理 3 条未解决映射**：过滤 `resolved=false` 的 appid，或在报告中列为剔除样本
3. **确定样本口径**：Q1 全量可用（成就数据完整）；Q2 中涉及 RAWG 特征的分析限定在 15,770 款

**下一步（建模）**：

- **Q1**：Rasch 1PL baseline → 2PL，报告收敛诊断，用全局完成率交叉验证难度参数
- **Q2**：参与度指标（时长/完成深度/活跃度/全成就比例）× 特征（类型、标签、价格、热度、难度结构）回归 + SHAP 归因，并明确「模型归因 ≠ 因果」
- **展示向成果**（可选，与老师沟通）：难度 × 弃坑四象限图、细粒度标签专题（如 Souls-like）、成就难度画像聚类
