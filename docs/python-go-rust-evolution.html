WHY GO / WHY RUST

Go 用简洁的网络编程与单二进制交付承接展示层；Rust 用所有权、原生编译与精细的内存控制承接推荐运行时。

Python 负责研究效率，Go 负责服务交付，Rust 负责资源密集的在线计算。三种语言围绕各自擅长的工作协作。

01

为什么从 Python 走向 Go 与 Rust

Steam 成就分析项目从数据采集、清洗和实验出发，Python 自然成为早期主力。它承担数据库提取、特征处理、分析与图谱准备，能够快速把研究结果跑通。随着成果需要通过常驻服务展示，研究环境和在线环境的资源需求开始分化。

服务器只有 2 核，还要同时承担 PostgreSQL 与面板。在线请求真正需要的是查询和展示，研究环境中的大部分依赖却继续进入部署链路；推荐服务即便已经复用持久缓存，也会在启动时建立大量内存对象。问题逐渐从“能否实现功能”变成“能否让这套功能长期稳定地运行”。

DASHBOARD / 交付效率

页面很轻，运行环境很重

读取报告路径触发科学计算栈导入，wheel 下载约 600 MB，服务器构建超过 11 分钟。展示服务需要更精简的依赖和更直接的发布方式。

RECOMMENDATION / 内存效率

输入已冻结，内存依然很高

图谱、游戏记录和多套索引以对象形式共存。本机基线空闲 Docker 工作集约 1.41–1.43 GiB，4 客户端并发时约 1.70–1.73 GiB。

两次迁移围绕不同目标展开：Dashboard 优先解决网络服务的部署复杂度与运行依赖，推荐服务优先解决图谱加载和评分过程的内存成本。Go 的服务开发效率、Rust 的资源控制能力，分别与这两类需求匹配。[1][2]

03

为什么选择 Go：把 Web 服务做轻、做简单

3.1 一个常量，穿透了整个依赖边界

原面板为了获取 REPORT_PATH，导入 modeling.regression.dataset。该模块顶层又导入 numpy / pandas，最终将 scipy、scikit-learn、SHAP、numba、llvmlite、matplotlib、seaborn、plotly 等研究依赖带进服务镜像。

展示服务需要：报告路径 → 读取 JSON → 返回 HTTP
实际导入链路：报告路径 → dataset 模块 → numpy / pandas
             → 科学计算与可视化运行环境 → 大量 wheel 与安装工作

2026-10-13 日志记录：wheel 下载约 600 MB，2 核服务器构建超过 11 分钟，原 Python 镜像约 2 GB。迁移后的首轮 Go 镜像约 16 MB，容器内存约 6 MB，镜像构建达到秒级。展示服务拥有了独立、精简的运行环境，发布从安装整套研究依赖变为交付编译产物。[1]

3.2 编译为原生程序，降低运行环境成本

Go 在构建阶段完成类型检查并生成机器码。HTTP 路由、JSON 编解码、文件读取和上游请求都在编译后的服务中执行。对于面板这种长期运行、功能明确的程序，一次构建后反复运行的交付方式非常合适。

静态类型也让跨模块改动更直接：接口参数、数据结构和错误返回的变化可以在编译时发现。面板从状态页逐步扩展为多个研究成果的入口时，统一的类型与编译检查减少了模块衔接的维护成本。

3.3 静态链接与交叉编译，让部署变成搬运成品

Go 服务使用独立 go.mod，数据库驱动为 pgx。本机通过 CGO_ENABLED=0 GOOS=linux GOARCH=amd64 交叉编译，将二进制与容器配置上传，服务器完成镜像组装和启动即可。首轮日志还记录了 vendor 依赖和离线构建。服务器不再需要仓库、Python 环境与科学计算工具链。

FROM scratch 只携带程序和必要文件，面板通过补充 CA 公钥证书验证 OSS HTTPS 连接，通过二进制自己的 -health 子命令完成健康检查。运行环境与应用一同确定，服务器上的安装步骤随之减少。

3.4 goroutine 与标准库，适合请求和 I/O 协作

Dashboard 的工作以网络 I/O 为主：浏览器请求页面、后端读取数据、代理推荐接口、传输研究附件。Go 的 net/http 已经提供服务器、客户端、路由和静态文件响应，goroutine 则提供轻量的并发执行方式，让不同请求在等待 I/O 时能够交错推进。

对于这类服务，Go 可以用接近顺序代码的写法组织请求处理，运行时负责 goroutine 调度。超时、请求上下文和取消信号也能沿 HTTP 调用链传递。项目中的推荐代理直接使用标准库 HTTP Client，展示层保持简洁，跨服务调用集中在清楚的接口上。

3.5 go:embed，让前端与后端一起交付

//go:embed 将小型 HTML、CSS 和 JavaScript 编入程序，UI 与后端版本一起变化，部署时只需交付对应二进制。对于由前端三件套组成的面板，这省去了额外的前端运行进程，也减少了静态文件漏传或版本错配。

Go 的自动内存管理让路由、响应结构和页面逻辑的开发保持直接；原生编译、标准库和交叉编译又满足了轻量部署的需求。开发效率与服务交付之间的这种平衡，是 Dashboard 选择 Go 的主要原因。

05

为什么选择 Rust：让内存随工作流释放

推荐服务的主要压力来自数据结构和评分工作区。Python 版本加载冻结输入后，游戏记录、图谱实体、关系集合和多套索引会共同驻留。字典、集合、字符串与动态对象让建模很方便，在大量细粒度关系上，也会累积对象元数据、引用和分配成本。面对几十万条关系，在线运行时需要更明确地决定“什么常驻、什么临时、什么留在磁盘”。[2]

5.1 所有权与借用，让对象生命周期清楚可控

Rust 通过所有权决定谁负责数据，通过借用允许函数访问已有数据。对于评分流程，种子画像可以在当前请求中复用，当前候选计算完成后即可退出作用域，最终结果只保留 Top-K 所需内容。程序结构能够直接表达这些不同的生命周期。

借用还能让函数通过引用读取数据，减少为了跨函数传递而进行的复制。当前实现中的 Reference<'a> 借用 SQLite 连接，并在请求内维护 IDF 缓存；编译器检查引用有效期，使连接与评分上下文之间的关系明确。

5.2 无需追踪式 GC，资源在作用域结束时释放

Rust 主要依靠所有权与 Drop 管理资源。局部对象离开作用域时执行清理，文件、查询对象和临时集合的生命周期与控制流对应。推荐计算会反复构建和销毁候选画像，这种释放方式便于让临时工作区跟着候选处理过程周转。

这一特性与 Go 的自动垃圾回收形成了不同的侧重点：Go 让 Web 业务开发保持简洁，Rust 则把更精细的内存和资源管理交给程序结构。推荐运行时强调低驻留内存，Rust 的控制能力正好匹配这一目标。

5.3 原生编译与类型化结构，适合计算内核

Rust 将循环、数值运算、集合遍历和分支编译为原生机器码。泛型与迭代器能够在保留清晰表达的同时参与编译优化，Vec 等容器也让元素类型与存储结构明确。项目使用 f64 表示分数、i64 表示 AppID，并将最佳列表保存为 Vec<(f64, i64)>。

编译期的类型、所有权和借用检查，为长期运行的服务提供内存安全支持。构建配置开启 LTO、单 codegen unit、符号裁剪与体积优化，再通过 musl 构建静态程序，形成约 3.98 MB 的 ARM64 scratch 运行镜像。

5.4 与 SQLite 配合，把数据留在磁盘

Rust 通过 rusqlite 访问 SQLite。games 保存候选资格、年份和搜索字段，entities 保存实体，relations 保存关系与原始证据，metadata 保存版本和实现绑定。正反向索引同样落盘，在线按需读取当前计算涉及的记录。[7]

这将语言的资源管理能力与存储设计连接起来：Rust 管理小型、短生命周期的工作区，SQLite 承担大规模持久数据和索引。整张图谱留在磁盘，应用内存集中服务于当前请求。

5.5 流式导入，控制准备阶段的峰值

导入程序逐段读取 gzip 快照与 JSONL，校验源文件摘要、版本、计数和候选资格，再逐游戏回放来源字段，核对实体、关系和证据。完整成功后才发布 SQLite 与摘要。这样，准备阶段不必先把全部关系文件解码为一棵巨大的通用 JSON 对象树。

本机在 1 CPU / 256 MiB 条件下完成全量导入与来源回放，约 116 秒。最终 SQLite 为 1,418,588,160 字节，通过磁盘索引支撑搜索、评分与证据查询。

5.6 小缓存与磁盘临时文件，控制数据驻留

PRAGMA cache_size = -8192;   -- SQLite 页缓存预算约 8 MiB
PRAGMA temp_store = FILE;   -- 临时排序等工作使用磁盘文件
PRAGMA mmap_size = 0;       -- 关闭 SQLite 内存映射
PRAGMA query_only = ON;     -- 在线连接仅查询

容器将宿主 scratch/ 磁盘目录挂载到 /tmp，用于临时排序等工作。应用保留种子画像、当前候选、IDF 缓存和最终解释，操作系统则负责文件页缓存，让磁盘读取能够复用已有页。

5.7 关系召回与 Top-K，让内存集中在有效结果上

当前评分先在 SQL 中按标签、类型、开发商的共同实体找候选，再叠加资格与年份条件，并排除种子本身。发行商权重为 0，不进入产生正分的候选召回条件。没有任何正权重关系交集的候选不会得到正分，因此在这套规则下可以跳过它们，保留全部正分结果的排序语义。

评分阶段逐行读取候选关系 ID，计算完成后尝试进入最佳列表。实现通过有序向量 Vec 和 partition_point 查找插入位置，再将列表截断为 K。排名列表只保存分数与 AppID，以 O(K) 的存储量维护当前最优结果。

5.8 排名之后，再组装完整解释

选出 Top-K 后，程序才为这些结果重新读取证据 JSON、来源事实、实体显示名和关系贡献，构建最终解释。大多数候选只需要参与计算，不必提前生成完整图谱路径。将“计算分数”和“组织证据”分成两步，可以减少重复解析和短命对象分配，同时保留正式结果的证据完整性。

5.9 串行请求与查询复用，减少工作区重叠

当前 tiny_http 服务循环逐个处理请求，共用只读 SQLite 连接，避免多个评分任务同时复制工作区。prepared statement 复用减少重复准备，单次请求中的 IDF 结果也会缓存以避免反复计算。[8]

服务将主要内存预算交给当前任务，评分完成后再处理下一项请求。与按需读盘、延后解释加载配合，形成了“磁盘存全量、内存做当前、结果留 Top-K”的在线运行方式。

06

优化计算路径，保留推荐含义

可解释推荐的迁移要同时保护排序和解释。相似度采用关系内 IDF 加权 Jaccard，标签 / 类型 / 开发商 / 发行商权重固定为 0.75 / 0.15 / 0.10 / 0。对每个关系分别计算相似度，再按权重加和；多个唯一种子采用等权平均。

idf(e) = ln((N + 1) / (df(e) + 1)) + 1
Jᵣ(A, B) = Σ idf(A ∩ B) / Σ idf(A ∪ B)
score(A, B) = 0.75 J标签 + 0.15 J类型 + 0.10 J开发商
joint_score(B) = Σ score(Aᵢ, B) / 唯一种子数

N 与 df 来自年份筛选后的合格参考候选，排除全部唯一种子；集合交并按同一关系计算。并集权重和为 0 时，该关系相似度记 0。公式中的发行商项因权重为 0 省略，原始事实仍可展示。

年份筛选必须发生在 IDF 统计之前。先按全量数据计算稀有度、再过滤年份，会改变某个标签在参考集合中的频率，进而改变分数。代码返回的 filter_order 明确标记为 year_filter_then_idf_then_rank_then_top_k。

缺失关系不重新分配权重，组合查询中不匹配的种子也保留零分份额。否则一个只匹配单个种子的候选，可能因为省略未匹配种子而获得不合理放大。同分结果按 AppID 升序，不生成随意的兜底推荐。

Rust 实现保留了与 Python math.fsum 对应的部分和策略，使数值累加顺序和舍入行为与原版对应。实现版本使用独立的 rust-* 标识，绑定相同冻结快照与图谱；语言迁移完成后，推荐依然能够沿着关系贡献追溯到原始事实。

7.1 Go 的收益集中在交付与运行环境

首轮 Go 迁移将约 2 GB 的 Python 镜像缩小为约 16 MB，服务容器内存约 6 MB。镜像里装入的是编译后的展示程序，研究依赖留在 Python 环境。发布更轻，运行时组件更少，部署过程也更直接。

7.2 Rust 的收益集中在数据驻留与内存

推荐版本从约 1.42 GiB 空闲进程 RSS，降至约 2.3 MiB；请求后 RSS 约 11.6 MiB，4 客户端并发下 Docker 工作集峰值约 156.4 MiB。SQLite 留在磁盘，Rust 为当前候选分配工作区，操作系统保留可复用文件缓存，三者共同构成低驻留的运行方式。

这版选择用更多磁盘读取换取低内存：串行单次推荐由 0.65–1.55 秒变为 2.48–3.41 秒，启动到接口就绪由 21.2 秒缩短为 13.2 秒。对于与数据库共享资源的小服务器，节省常驻内存是这次推荐运行时迁移的核心目标。

RSS 为进程驻留内存，Docker 工作集采用 cgroup usage 减 inactive_file 的统计口径。GiB / MiB 为 1024 进制，镜像与磁盘 MB / GB 为十进制。

08

部署优化：程序变化，不必搬动全部数据

8.1 Go embed 从便利开始，也会积累重量

最初把 HTML / CSS / JavaScript 内嵌到 Go 二进制，能减少文件丢失和发布错配。研究成果不断接入后，LYX 原页、图片与来源附件成为主要体积来源，评估统计的 85 份内嵌资源约 19.75 MB，其中 LYX 约占 91%。服务进一步采用“小型 UI 内嵌、大型成果持久化”的交付方式。

实现保留小型 UI 内嵌，将 73 个冻结内容文件、共 21,016,856 字节放入持久 content/：LYX 原交付 60 份、研究原图 10 张、两份汇总 JSON 和一份历史报告。拆分后交付记录中的 Linux Go 二进制约 11.95 MB、代码压缩包约 4.57 MB。[3]

8.2 内容寻址，解决反复上传

同步流程比较服务器文件的实际 SHA256，复用已有相同对象，只上传缺失、变化或损坏内容。新 release 的全部文件校验通过后，原子切换 current 指针；旧版本保留用于恢复。容器只读挂载 content 的父目录，使指针切换可以在容器中被看到。

历史本机部署演练传输结果优化点

相同内容再次同步0 数据字节程序更新复用已有成果

上传中断 / 版本不完整拒绝切换，旧版本继续提供避免半新半旧的成果展示

8.3 程序轻量化，成果保持完整

LYX 原页包含约 5.22 MB 内联 JSON，并通过相对路径访问文档、原图与 CSV / JSON 明细。如果只迁移入口 HTML，附件会断链。因此内容拆分保留完整交付树、原字节和相对 URL，Go 使用文件服务按结构读取，没有为了减小程序而裁剪成果。

8.4 推荐数据库，同样与程序版本分离

Rust 数据库存放在 data/versions/<SHA256>/，data/current 指向启用版本。已有相同摘要且实际校验通过时，部署可跳过数据上传。镜像和数据分别有身份，程序小更新不需要反复搬动约 1.42 GB SQLite。旧数据与旧镜像保留，切换前验证完整性，避免程序启动后才发现数据缺失。

SQLite 承担冻结推荐数据的在线查询，PostgreSQL 保存项目原始数据。数据准备与在线运行分开后，推荐请求直接使用已发布的 SQLite，程序更新也可以复用已有数据版本。

09

轻量交付：构建在本机，运行在服务器

Go 与 Rust 都能交付独立的原生程序，让开发机承担构建工作，服务器专注运行。Go 直接交叉编译 linux/amd64 二进制，Rust 则在本机构建目标镜像，发布后由服务器加载。两套服务都采用 scratch 运行镜像。[5]

Rust 上线时，原方案还需要在服务器将 Python 冻结缓存导入 SQLite。当时主机 swap 已占满，导入两次阻塞。调整后，SQLite 也在本机通过刚构建的镜像生成，该次日志记录约 1 分钟，再将完成品上传。服务器负责“接收 → SHA256 校验 → 原子切指针 → 启动”，编译与全量数据准备都移出了生产环境。

早期部署路径
上传程序 → 服务器导入完整图谱 → 与 PostgreSQL / 面板争资源 → 启动

修正后的部署路径
本机编译镜像 + 本机生成 SQLite → 上传完成品
→ 服务器校验摘要 / 完整性 → 原子切换版本 → 启动只读服务

最终部署撤掉了 cpus: 1 / mem_limit: 256m 的硬限制，保留只读根目录等运行配置。面板目标由 8605 切至 8606，代理的 meta / search 返回 rust-graph-score-v1，原 Python 线上推荐实例被移除。

这让两次语言迁移形成统一的发布习惯：本机生成确定的程序和数据，服务器校验并启用对应版本。运行环境随交付产物确定，生产主机上的安装和准备步骤随之减少。

10

迁移效果：轻量运行，保留原有功能

10.1 Go：从接口行为开始对照

首轮迁移先保存 Python 版 6 个接口响应作为基线，再对 Go 输出逐字段递归比较，覆盖 NUMERIC 百分比、数组、NULL、447 条标签和两组共 75 条成就。最后只保留 3 处有意删除的 fetching 字段差异。浏览器验收检查通过，页面脚本错误为 0。[1]

时间字段统一转为 UTC，并分别在上海、UTC、纽约时区验证，使 Go 版本在不同机器上保持相同的序列化格式。

10.2 Rust：把分数、排名和事实一起核对

ARM64 与最终 AMD64 Docker 镜像分别完成 69/69 项真实接口对照。每轮包含 138 次请求、23,443 个数值比较、2,728 条来源事实和 1,364 条解释路径，数值容差 1e-12，覆盖完整排名、权重、组合种子、年份筛选和解释图。[3]

全量导入还逐游戏回放来源，核对所有事实与证据。Go 面板接 Rust 后，桌面与手机验收覆盖真实推荐、组合、年份、证据、空结果、失败重试和路由。界面可用、接口相符、数据绑定正确是不同层面的验收，需要同时成立。

Python 让研究快速展开，Go 让 Web 服务轻装交付，Rust 让推荐计算的资源使用更精细。语言优势最终落在了项目最需要改善的环节。
