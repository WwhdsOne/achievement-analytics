achievement-analytics · 数据获取流程

这份页面解释项目的数据是怎么一步步抓进 PostgreSQL 的：谁先谁后、花了多少请求、 断了怎么办、多台机器怎么一起跑。面向全组同学，不需要先读代码。

核心问题：玩家更愿意玩什么样的游戏？ —— 先得有足够多的游戏数据。

01我们到底在抓什么

目标总体：2026 年以前发售、带 Steam 成就的游戏——成就是本研究（难度建模 + 偏好归因）的基础信号， 没有成就的游戏进不了任何分析。规模是实测采样估计，不是拍脑袋：

口径数量（估计）说明
Steam 全部游戏≈ 186,800官方 GetAppList 全量接口，4 次请求拿完
其中带 Steam 成就≈ 81,850商店筛选出（数字每日浮动）
再限「2026 年以前发售」≈ 49,900我们的数据范围（占 61%；2026 新作与无发售日的排除）
其中 RAWG 有任务评价数 ≥ 100 的子集配额太贵，只给有知名度的游戏（见 06 节）

02全景：三步走

整个数据侧只有三个入口命令。所有状态都存共享云库（PostgreSQL），本地不留任何数据文件。

第 1 步 · 种子枚举「都有哪些游戏」
翻 Steam 商店搜索页（一次 100 款，按发售日降序），把每款游戏的名字、发售日、评价数、价格写进 games 和 store_search_games。约 819 次请求、14 分钟，免 API key。
uv run python -m cleaning.seed
↓ 枚举完，把「每款游戏 × 每个逐款数据源」展开成待办清单
第 2 步 · 物化生成任务队列
约 5 万款游戏 × 6 个逐款源 → 约 30 万行任务写进 fetch_tasks 表，初始状态 pending。之后抓多快、抓多少，全看这台「队列」。由种子命令带 --materialize 参数一并完成，也可以事后单独补物化。
↓ 任何人、任何机器都可以开始干活，随时中断随时续
第 3 步 · 回填worker 循环干活
反复「抢一批任务 → 抓数据 → 写库 → 记进度」，直到队列清空。Ctrl-C 随时中断，重跑自动续。多台机器共用一个云库同时跑，互不重复。
uv run python -m cleaning.worker
为什么这么设计？ 好处有三个：可中断（进度全在库里，断了就断）； 可观测（还缺什么查一下视图就知道）；可并行（加机器就是加吞吐，不用改任何代码）。 老方案是「一个大脚本顺序跑八万款」，第 30 小时才暴露 bug，谁也耗不起。

03九个数据源：6 个逐款 + 3 个批量

每款游戏的数据来自多个公开接口，分两类：bulk（一次请求拿一批，不走任务队列） 和 per_game（一次请求拿一款，进队列）。逐款源按 priority 排队，序号小的先抓。

源类型给什么数据限速配额key优先级
appdetails_enper_game 游戏详情（英文）：类型、发行商、 genres / categories 1s—免10
global_achper_game 全局成就完成率（每个成就的全球解锁百分比） 1s—免20
community_achper_game 成就的展示名（中文可读名称，与上一源按位对齐完成映射） 1s—免30
appdetails_zhper_game 游戏详情（简中）：本地化名称与描述 1s—免40
steamspyper_game 拥有量区间、SteamSpy 侧标签与时长分布 1s—免50
rawgper_game 社区评分、平均时长、弃坑 / 通关人数、metacritic 1s20,000/月/key需90

另有三个 bulk 源不走队列：商店搜索（种子用）、store_applist（全量 appid 校验）、 steamspy_all（1000 款/次，间隔 60s）。权威定义在 schema.sql 的 sources 表，代码侧 crawler/registry.py 与之保持一致，有测试断言。

04一条任务的旅程（状态机）

任务只有五种状态，其中三种是「确定性终态」——这是整个队列能收敛、不会无限重跑的关键。

pending排队中
→ 抢占（写 5 分钟租约）→
ok抓到了
pending
→
empty接口确定没数据
（如无成就 403）
·
skipped被剔除
（该游戏无成就）
·
error失败，退避后可重试
→ 重试 3 次仍败 →
exhausted放弃，待人工
确定性终态的意义：empty 和 skipped 不会重试。比如某游戏根本没有成就数据 （接口返回 403），确认一次就够了——它其余 5 个源的任务会被立刻取消 （skipped），尤其是最贵的 RAWG 一分配额都不会花。

05多台机器怎么不打架

原子抢占：一条 SQL 选任务 + 占座

worker 每次用一条 UPDATE ... WHERE ... IN (SELECT ... FOR UPDATE SKIP LOCKED) 同时完成「挑 20 条待办」和「写下租约」。数据库行锁保证两台机器不可能抢到同一条—— 谁先锁到行谁拿走，后来的直接跳过（SKIP LOCKED），不排队不等待。

租约：worker 崩了也不用清尸

抢到的任务有 5 分钟租约（claimed_by / lease_until）。 处理完正常回填；如果 worker 半路崩溃，租约到期后任务自动回到可抢状态—— 不需要任何人去清理「僵尸任务」。

前提只有一个：连同一个库

队列、配额账本、RAWG 密钥池全在共享的 PostgreSQL（腾讯云）里，各机器 .env 配同一个 POSTGRES_HOST 即可。例外：RAWG 的配额绑定 API key 而不是机器， 所以加机器对 RAWG 没有加速效果，扩容只能加 key（见下节）。

06最贵的 RAWG：三条护栏

RAWG 是唯一按量计费的源（20,000 次请求/月/key，响应头不显示剩余额度）， 实测约 6.3 次请求才能处理一款游戏——单 key 一个月只够约 3,100 款。 所以它排在优先级最后，并配了三条护栏：

护栏一 评价数阈值

物化任务时，商店评价数 < 100 的游戏不建 RAWG 任务。 试水证实低评价游戏在 RAWG 上几乎必然没数据（100 款冷门游戏：72 款搜不到、 28 款搜到也近乎空表）。阈值可用 --rawg-min-reviews 调整。

护栏二 无成就先剔除

RAWG 优先级（90）排在 global_ach（20）之后：一旦某游戏被确认没有成就， 它的 RAWG 任务在同批次内就会被跳过，配额一分不花。

护栏三 密钥池 + 记账

所有 key 注册进共享库的密钥池，每次请求原子地挑一个本月还有余额的 key 并计数。 余额查 rawg_key_status 视图（只显示尾 4 位，不暴露明文）； 每一次真实请求都记进 api_usage 账本。

义务 非商业 + 回链

RAWG 免费档限非商业用途（课程项目符合），且要求在使用数据的页面加 RAWG 回链——这条义务要在最终报告 / 展示页里落实，不是可选项。

07防止把事情搞砸的几道保险

限速 按源配置，不是一刀切。Steam 系 1s、SteamSpy 批量接口 60s（官方要求）。 计时按域名分桶——Steam、SteamSpy、RAWG 互不排队，总耗时不会白乘三倍。
退避 失败重试之间强制指数退避（2s / 4s，封顶 30s）。没有退避时几次重试会挤在 同一个限流窗口里全部撞墙——实测这样打断过一次 819 页的枚举。
断点续传 商店枚举被限流时记下「空洞」偏移并继续，跑完报告空洞数；重跑只补洞。 有空洞 = 帧不完整 = 不能开始全量抓取，这是显式的质量闸门。
不中断 单条任务失败只记日志 + 退避，绝不中断整批；批内异常兜底成 error 状态， worker 进程永不因一条坏任务崩掉。
审计 fetch_tasks（可变的当前状态）与 ingest_log（不可变的抓取历史） 分工明确：前者回答「该抓谁」，后者回答「什么时候抓的、结果如何」。
PostgreSQL 是唯一事实源。 项目没有本地文件缓存——防重复完全靠任务状态， 删库 = 全部重抓 + 重花 RAWG 配额。所以云库自动备份（按天快照）是硬性要求。 data/ 目录在建模阶段才启用，原始数据永远不进 git。

08入库之后：三条硬规范

成就名必须用展示名

全局完成率接口给的是 ACH41 这类内部名；社区页给的是可读展示名。 两源顺序一致、按位对齐完成映射，落在 achievements.api_name → display_name。 正式分析与报告只允许出现 display_name，内部名禁止出现。

建模绑定数据版本

全局完成率会随时间漂移（今天的完成率 ≠ 下个月的）。建模前在 dataset_versions 登记固定版本号，保证实验可复现； 追溯真实抓取时间看各表的 fetched_at。
