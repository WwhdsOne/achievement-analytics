# 刘宇翔：主线进度漏斗与成就参与分析总体规划

更新日期：2026-10-14。负责人：刘宇翔。本文是任务总览与实施路线；数据库细节见[database/README.md](database/README.md)，程序与指标细节见[process/README.md](process/README.md)，来源试跑记录见[process/API_PROBE.md](process/API_PROBE.md)。

## 1. 任务定位与最终要回答的问题

本模块对应项目[docs/plan.md](../../docs/plan.md)中的“主线进度漏斗与成就参与分析”。项目实现方向与根目录AGENTS.md旧描述冲突时，按用户明确要求采用docs/plan.md和本次讨论确定的研究内容。

**核心问题：不同游戏标签是否与主线推进、通关表现相关？支线、收集、挑战等可选目标的完成情况，能否结合时长和难度信息，解释玩家投入方式的差异？**

分析按三个层次组织：

| 层次 | 任务 | 要解释的现象 |
|---|---|---|
| 核心：主线推进 | 识别并人工核验主线节点，形成剧情进度漏斗；比较游戏标签与完成表现 | 人群推进到哪里，不同游戏特征对应怎样的差异 |
| 辅助：可选参与 | 对成就做语义分类，区分接触与深入完成，分析支线、收集、挑战等目标 | 主线之外有哪些投入方向，主线完成较低是否伴随其他参与 |
| 补充：投入与条件 | 使用有效时长、难度印象标签和明确挑战条件；外部攻略估计仅作为可选来源 | 完成表现与投入规模、目标要求是否呈现一致或不同的趋势 |

成就分类是形成可解释指标的基础工作，不是贴完标签即结束；也不能只找主线而忽略用户明确关心的可选参与方式。最终产物应包含主线漏斗、辅助参与画像、标签关联分析及有覆盖说明的时长对照。

## 2. 研究范围与工作约束

- 所有新增和修改只发生在result/LYX；其他目录永久只读。database存本地建表SQL与输入，process存处理逻辑与运行记录，本文与两个子目录同级。
- 共享PostgreSQL只读提取，不修改共享表、队列、配额、版本登记或其他成员成果。本地SQLite保存所选游戏的固定副本和标注，不回写云库。
- 分析单位是游戏，数据是人群聚合量。不能识别普通玩家与硬核玩家，不能确认同一批玩家同时通关、收集或游玩较久。
- “用户粘性”操作化为主线推进与可选内容参与等代理表现；没有个人历史与时间序列，不计算回访留存、真实流失或弃坑生存曲线。
- 研究结论描述关联，不把“带某标签的游戏完成表现不同”写成“该标签导致变化”。本模块不恢复旧方案的逐玩家能力建模，也不先合成粘性总分。
- 正式选样遵守项目既定发行年份范围，核验实际发行信息；来源演示网页不自动成为分析样本。先两款FF7，再20～30款试点；100～1000款是质量允许后的扩展目标。
- 原始输入、SQLite文件、备份和运行原始响应不提交Git；凭据不进入输出。commit、amend、push仍需明确指示。

## 4. 数据源与处理路线

优先使用已经存入共享库的数据，避免重复请求和消耗配额；外部站点只承担必要的补充核验或获准的数据提供。

| 数据源 | 需要的属性或内容 | 获取与处理方法 | 使用边界 |
|---|---|---|---|
| 共享库：games、achievements | appid、展示名、描述、原始position、api_name、percent | 只读SQL提取，按appid和成就身份关联，保存固定快照 | position不是剧情顺序；api_name只用于内部关联，正式展示用display_name |
| 共享库：game_tags | tag、source、votes、kind | 分别提取，保留原始值；对大小写、语言与同义词建立版本化映射 | 排除平台功能标签；缺标签不等于无某种特征；多标签组会重叠 |
| Steam商店/SteamSpy的已存属性 | 发行日、类型、评价数、热度等实际已有字段 | 用于选样与比较背景，先核实来源和可用性 | 热度、拥有量、当前在线不是精确销量或留存；SteamSpy当前时长字段不可用 |
| RAWG的已存数据 | rawg_id、name、playtime、fetched_at；必要时查看状态计数 | 先使用库内正值并核验版本；时长组成独立补充子样本 | 实际时长不是通关所需时间；RAWG状态与Steam成就人群不同，系统跨源状态对比不是首版必需任务 |
| Steam官方接口与社区成就页 | 官方全局完成率、展示名、条件文本 | 已有数据不足或需核验时，按公开接口/页面及来源限速处理 | 全局率与个人记录不同；核验时记录抓取时间，不无版本地覆盖旧快照 |
| Steam Hunters公开API | 成就名称、描述、Steam百分数及有限分组 | 可沿用已有小样本程序；按apiName映射核验，不按位置猜匹配 | 当前已核验API没有主线/支线/收集语义分类；站内localPercentage不能冒充Steam全局率 |
| Gamer Guides | 可能的成就类型、路线、Time与Difficulty | 来源与语义核验；获准接口、导出或采集方式明确后才考虑批量适配 | 初始HTML可解析不等于获得数据集许可；攻略估计范围、作者和方法待核实 |
| TrueSteamAchievements | Main Storyline、Collectable等flags定义及可能的成就分类 | 已有定义资料可辅助制定规则；能返回分类的通路仍需核验 | 样本请求曾遇Cloudflare 403，公开分类API未核实，不作为当前稳定依赖 |
| PowerPyx等攻略资料 | 剧情章节、结局、困难模式和解锁限制的依据 | 按允许的研究使用范围核验，记录链接与具体依据 | 未核实结构化分类API；此前证书问题不通过关闭TLS验证解决，不默认批量抓正文 |
| 人工判断与自定义规则 | 内容类型、路线、前置关系、目标强度 | 小样本参考标注、关键词baseline、人工修订；模型辅助后置 | 规则/模型输出是建议，不能伪装成网站原生标签或自动批准 |

### 已确认的时长与难度口径

1. SteamSpy平均/中位时长在此前50,741条记录中全部为0，不用于时长分析。
2. RAWG有15,770条记录，其中11,648条playtime>0，约覆盖全库22.9%；零值含义未确认，首版分析排除并单列。来源抓取集中于2026-09-18至10-01，且上游选样偏向评价数较高的游戏。RAWG官方介绍称Steam平均游玩时长，单位为小时，但抽样与计算窗口未充分披露。
3. 重生库内playtime=71小时；重制版为0，关联RAWG名“Final Fantasy VII”存在版本疑点。暂停后者RAWG证据，不因此否定Steam成就分析；正值也需要质量检查。
4. game_tags已有Difficult、Unforgiving、Souls-like、Adjustable Difficulty等标签。困难印象、低容错、玩法类型和可调机制应分别解释，不能统一当难度等级。Difficult跨来源去重覆盖4,813款是此前核验值。
5. achievements.description中的困难模式条件可支持challenge标注。game_difficulty的分位数、最小率和hard_ratio来自解锁率，先解释为成就稀有程度，避免用同组完成率构造“难度”再解释完成率。
6. Gamer Guides示例初始HTML有25–38h和6/10；很可能是成就路线估计，但范围尚未核实。预计耗时不替代实际游玩时长，6/10不直接称普通主线客观难度。

核验明细、单位及来源链接见[database数据口径](database/README.md#补充数据的核验结果与取用口径)。

## 5. 分阶段任务

### 阶段一：确定指标与两款FF7的语义参考

**目标：先证明成就可以被正确解释，再写批量程序。**

需要做：

1. 阅读两款游戏的完整成就清单，建立mainline、side、collection、challenge、multiplayer、dlc、other、unknown的多标签规则。unknown不能与已明确类型共存。
2. 对主线确认入门、前期、中期、后期、结局的代表节点、剧情顺序、必经性及前置关系；本体与INTERmission分开，困难通关与普通主线分开。描述缺失、分支或证据不足时保留待核验。
3. 为支线、收集、挑战选择可以代表接触和深入完成的目标，记录条件强度与接触机会。若某类没有合适成就，标为不可观测，不虚构指标。
4. 建立人工参考清单，记录证据URL、判定理由、审核人/时间、未知与争议。成就可以同时具有主线内容和挑战含义，但进入普通主线漏斗还需单独核验。

**交付物：** 标注规则初版、两款游戏的审核清单、主线路线与关系清单、辅助目标清单、证据缺口台账。

**验收：** 每个拟发布节点和关系都有人工依据；章节候选没有直接变成批准结果；目标强度与类别分开，展示名与身份可追溯。两款游戏只用于验证方法，不推断整个市场。

### 阶段二：固定分析输入与本地数据结构

**目标：让后续标注和分析始终使用可复现的同一份输入。**

需要做：

1. 保存样本appid、实际发行信息、选样与排除原因；导入时重新只读检查未解决映射，而不是永久沿用旧的3款问题名单。
2. 分别读取游戏、成就、标签、必要背景字段与RAWG信息，避免一对多联表把成就重复展开。连接与事务强制只读，设置查询超时并及时关闭。
3. 在database内建立SQLite，保留原成就字段名、身份键与可空语义；新增dataset_version和SHA256。原始快照不可覆盖，源抓取时间与本地提取时间分别保存。
4. 明确标签快照、RAWG质量标记、辅助目标强度和核验关系的本地数据契约，再扩展现有六表SQL。数组按关系表或明确序列化规则处理，SQLite类型限制按程序与约束共同验证。
5. 数据文件、备份放本地受忽略路径；采用单写入者、短事务，外键开启，按database README的已核验运行时注意事项选择日志模式。

**交付物：** 本地结构与数据字典、导入程序、两款游戏的固定输入版本、样本/来源时间/质量报告。

**验收：** 行数、身份唯一性、单位、空值、外键、来源与指纹可核对；重跑不覆盖旧快照，无远端写入。SQLite足以支持100～1000款个人标注，首版没有复制百万级全库的必要。

### 阶段三：实现初标、审核与可恢复处理

**目标：减少重复人工工作，同时保留人工对语义和关系的最终核验。**

需要做：

1. 以展示名、条件文本和必要游戏上下文实现关键词baseline。percent不用于判定内容类型，章节号只是顺序候选。
2. 输出多标签、理由、证据、规则版本与输入指纹，自动结果保存为suggested。有必要再评估模型辅助，记录模型和提示词版本；不跳过规则对照直接依赖模型。
3. 提供本地审核文件或简单审核入口，支持修订类型、确认路线/目标强度、说明争议并保存审核记录。人工approved结果不被后续自动运行覆盖。
4. 单项标注及标签原子落库；网络/模型调用在事务外。按数据版本、标注版本和成就身份续跑，调用失败进入运行日志和待处理，不当作最终unknown或无数据。
5. 与人工参考比较各类误判、漏判和未知覆盖；主线节点和前置关系另验。参考样本有限时只报告该样本结果，不能声称普遍准确率。

**交付物：** 初标程序、审核入口、版本化标注结果、错误与修订记录、小样本质量评估。

**验收：** 发布数据有审核依据，自动建议与确认结果明确区分；重复运行保护人工成果；未知、不可观测、真实零值与程序失败不会混淆。

### 阶段四：扩展20～30款试点并整理游戏特征

**目标：得到可以进行初步比较的样本，验证不同游戏之间的口径。**

需要做：

1. 按主线清晰、成就映射可靠、标签可用选样，兼顾不同类型、年份和热度。指定少量研究标签，如开放世界、剧情、探索及难度印象；不在极小样本里同时比较大量标签。
2. 保存选样清单和标签组覆盖；人工选择说明便利样本偏差，随机过程固定random_state=42。多标签组可重叠，不假设互斥。
3. 统一标签表达，保留来源与原始票数，剔除平台功能标签；缺标签与没有标签特征分开。每款游戏人工确认主线节点，并审核纳入辅助指标的成就。
4. 比较辅助目标强度和接触阶段，防止用“首个收集物”与“全收集”直接排名。记录审核覆盖、类别缺口与无法比较的原因。
5. 将RAWG正值且版本可靠的游戏作为补充子样本，比较加入时长前后的游戏与标签分布；缺时长不删除其主要成就分析。

**交付物：** 试点输入/标注版本、标签映射、游戏特征表、主线与辅助目标表、主要/时长子样本覆盖报告。

**验收：** 样本可重建，排除原因明确；主要标签组的样本量可见；主线关系与辅助目标口径可解释。正式主线长度若没有可用数据，明确列为局限，不把RAWG时长或全成就预计时间充当已控制的主线长度。

### 阶段五：计算指标、验证假设与生成图表

**目标：用可解释的指标回答研究问题，而非只展示分类数量。**

| 指标/分析 | 处理方法 | 成立前提与输出边界 |
|---|---|---|
| 主线漏斗 | 按人工剧情顺序展示关键节点的全局解锁率 | 不按解锁率或原始position排序冒充剧情 |
| 入门者通关比例 | p_f / p_s | 结局解锁必然先有入门解锁、分母/时点口径一致且p_s>0；不叫留存或弃坑率 |
| 阶段条件比例 | 后续率 / 前置率 | 逐对核验嵌套；超过1或关系异常时报告问题，不裁剪强算 |
| 可选参与画像 | 已审核代表目标的单项率、类别均值及分布 | 接触/深入完成分开；均值描述纳入的目标组，不是参与人数或全成就玩家比例 |
| 游戏标签比较 | 组内分布、中位数、差异与代表游戏对照 | 样本单位是游戏，多标签共现与样本选择可能解释差异 |
| 时长辅助分析 | RAWG有效子样本散点、Spearman相关和类型/年份等分层对照 | 长时长还可能来自内容长、反复尝试、刷取或挂机；不能证明喜欢或因果 |
| 可选简单模型 | 样本与字段足够时再做简单回归及验证 | 先描述分析；避免泄漏与用同组完成率反推“难度”后解释自身 |

类别平均解锁率不能推断解锁过至少一个该类成就的人数比例；多结局不能直接相加；任何辅助目标率除以前置率都需要核验必然关系。没有合适目标、审核不足与真实率为0必须区分。多个成就来自同一游戏，不能当作多个独立游戏样本扩大统计证据。

优先检验以下假设，均不预设为发现：

- 开放世界等标签是否更常伴随“主线较浅、支线或探索较高”的组合；时长是否提供一致的补充趋势。
- 主线完成较好而时长较短的游戏，是否主要属于紧凑剧情体验；不能直接判成低粘性。
- 挑战稀有而时长较长，是否可能对应重复尝试或其他投入，而非简单的“不愿意玩”。
- 收集较普及却时长不高，是否与顺路获得、目标较浅或成就设计有关。

**交付物：** 单游戏主线漏斗、可选参与画像、标签组比较图、时长子样本对照、异常报告和解释文字。每张图绑定数据/标注版本、样本数和指标定义，正式展示仅用display_name。

**验收：** 公式前提有检查，覆盖和缺失可见，结论区分观察事实、候选解释与尚未排除的因素。发现同样重要的是无明显差异或数据不足，不能为了反直觉故事挑选结果。

### 阶段六：质量允许后扩样与最终交付

**目标：在稳定口径上逐步靠近项目100～1000款目标，并形成可审阅成果。**

需要做：按人工核验能力分批扩样，重新检查标签/时长/类别覆盖和选择偏差；沿用固定版本与审核机制。记录最终样本、方法、参数、图表、反例及局限，与组内相关模块保持可复用的字段与标注定义。

## 6. 外部攻略数据的独立可选路径

Gamer Guides等来源不阻塞以上主流程。2026-10-14核查的[Gamer Guides条款](https://www.gamerguides.com/terms)第3/5节限制系统采集与数据集用途，要求事先书面许可；HTML可读、课程非商业用途或改为手工系统摘录不自动解决授权。

接入顺序为：确认允许的用途/导出或采集方式 → 核实主线或全成就范围、平台/版本、DLC、作者与方法 → 小样本验证映射/字段覆盖 → 独立适配与质量标记 → 作为补充特征开展敏感性分析。

获得许可后仍按约定频率访问，避免重复请求；挑战/限流挂起来源并记录原因，不绕过，也不记为无数据。一次200不能证明批量不会触发风控。外部难度和时间分别命名为攻略估计，保留原值、量表、区间、来源与范围未知状态，不覆盖RAWG实际时长。
