# 刘宇翔：主线进度与成就参与分析实施规划

规划更新日期：2026-10-14。研究内容按[docs/plan.md](../../../docs/plan.md)及本次讨论确定，主问题是：**不同游戏标签是否与主线完成表现相关？支线、收集、挑战等参与方式及有效时长，能否帮助解释这些差异？**

所有程序放在result/LYX/process，本地建表SQL与输入快照放在result/LYX/database；其他目录永久只读，远端数据库只读。当前阶段是完善口径与两款游戏试点；本文是实施规划，本次仅更新README，没有启动导入、模型或批量网站采集。

## 研究内容与责任边界

| 层次 | 要完成的内容 | 结果用途 |
|---|---|---|
| 核心 | 人工确认主线节点与前置关系，按剧情顺序形成漏斗；比较游戏标签与主线完成表现 | 回答游戏特征与剧情推进的关联 |
| 辅助 | 多标签分类，并区分支线、收集、挑战的接触与深入完成目标 | 解释玩家把额外投入放在哪些内容上 |
| 补充 | 在有效RAWG子样本中加入时长；使用难度标签和条件文本 | 检查完成表现是否伴随不同投入规模与目标条件 |

成就分类是分析依据，不是独立终点，也不缩减成“只找主线”。首批对完整成就清单初标，人工优先核验主线和典型辅助目标，再逐步补齐类别审核。与组内分类完成曲线模块保持字段、标注版本和指标定义可复用；RAWG玩家状态的系统跨源对比不列为本模块首版必需交付。

现有数据是游戏级聚合，不能识别普通/硬核玩家，也不能确认同一批人同时做支线、通关或游玩较久。报告研究的是人群完成表现的关联，不写“标签导致通关率改变”。没有逐玩家或连续历史数据，不做回访留存、弃坑生存分析、玩家能力估计，也不先合成一个“粘性总分”。

## 指标契约：先确定含义，再写分析程序

### 主线进度

保留各节点的全局解锁率，按人工story_order展示，不能按percent或原始position排序冒充剧情顺序。首版优先入门、前期、中期、后期、结局等代表节点；不存在合适成就的阶段保留缺口，不虚构节点。

设入门解锁率为p_s，结局为p_f。仅在结局解锁者必然先解锁入门节点、统计人群和时点口径一致、p_s>0时，计算p_f/p_s，命名为“观察时点内入门者的通关比例”。例如80%与32%得到40%，只是公式示例。

- 相邻节点比值也要逐对核验嵌套，不能因两个节点都标为mainline就直接相除。
- 困难模式、速通、无伤、二周目或DLC章节另记条件/路线，不混入普通主线漏斗。
- 多结局分别报告；没有个人联合记录时不能直接相加作为总通关比例。
- 比例超过1、剧情前置倒置或无法证明嵌套时，输出异常与原始率，不裁剪、不强算。
- 没有通关的人可能尚在游玩，也可能放弃；上述比例不叫留存率，1减去它不叫弃坑率。

### 支线、收集、挑战等辅助参与

同一类别先辨认目标强度和接触机会，再统计完成情况：

| 类别 | 接触/较浅目标的例子 | 深入目标的例子 | 需要解释的条件 |
|---|---|---|---|
| side | 完成首个可选任务 | 完成系列或全部支线 | 是否早期可接触、是否必须先推进主线、是否有强奖励 |
| collection | 找到首个收集物 | 达到较高收集门槛或集齐 | 顺路获得、探索规模、随机性与累计耗时 |
| challenge | 完成一项明确特殊挑战 | 高难、速通或严格限制目标 | 技术、时间、重复尝试和可选参与都影响完成率 |
| multiplayer / dlc | 参与对应模式/内容 | 完成对应系列目标 | 联机可用性与DLC拥有量未知，需单独说明适用人群 |

这些例子不是每款游戏必备的指标。只有通过人工核验、确实代表目标的成就才可采用；“接触机会→选择尝试→有能力和时间完成→成功触发”共同影响解锁率。高完成率不自动等于喜欢，低完成率不自动等于难。

可以报告纳入审核的某类成就平均解锁率、分布，以及代表目标的单项率，并同时列出纳入项数、审核覆盖和遗漏/争议。若所有指标使用同一人群分母，类别均值表示这组目标的平均完成比例；不能叫“参与该玩法的人数占比”或“全成就玩家比例”。不同游戏目标强度与成就构成不同，类别均值先作为辅助画像，不能直接按高低判定粘性。

例如两个收集成就解锁率40%、20%，平均30%；在同一分母下，至少解锁一个的人群占比只能确定在40%～60%之间。确有“首次参与”成就时，它的解锁率可描述所代表的接触行为。辅助目标率除以入门率或接触目标率，同样需要核验必然前置和共同分母；不能统一除以p_s就称条件参与率。

多标签类别不互斥。没有该类成就、没有完成审核、描述不足与真实解锁率为0是不同情况，前几项保持不可计算/未知，不补成0。联机和DLC保持独立条件；缺少对应人口分母时不强行校正。

### 时长与难度证据

- SteamSpy两列时长在此前50,741条记录中全部为0，首版不使用。RAWG时长取playtime>0的候选值，并核验匹配、异常与抓取时间；“攻略预计耗时”单独记录，不能替代实际时长。
- 使用两个样本集合：有可靠成就标注的主要样本，以及其中RAWG正值且匹配可靠的补充样本。主要分析不因缺少时长而丢掉游戏；加入时长前后分别报告样本及标签分布，避免把样本变化当作时长解释。
- FF7重生库内playtime=71小时；重制版为0且RAWG名称存在版本疑点，暂停后者的RAWG补充证据，保留其Steam漏斗分析。正值也不是主线通关所需时间。
- Difficult、Unforgiving等来源标签可作为难度印象特征；Souls-like与Adjustable Difficulty分别表示玩法和可调机制。没有标签不代表容易，票数不等于难度等级。
- description中的明确困难模式条件用于challenge初标和人工核验。game_difficulty的hard_ratio等是解锁率分布，分析时称稀有程度，避免把同组完成率构造的特征当作独立难度原因。

## 可检验的辅助问题

以下均为待检验假设，不能预写成发现，也不从聚合量推断个体动机：

| 可能的表现组合 | 候选解释 | 需要排查的替代解释 |
|---|---|---|
| 主线完成较浅，但探索/支线较高、时长较长 | 自由探索或可选内容承载了投入 | 游戏较长、仍在游玩、支线早期即可完成、奖励驱动 |
| 主线完成较好，但时长较短 | 紧凑剧情便于完整体验 | 内容长度、难度设置和样本口径不同，不能判成低粘性 |
| 挑战较稀有，但时长较长 | 反复尝试或其他玩法占用时间 | 刷取、挂机、兴趣或解锁条件，而非一定是技术难 |
| 初期推进较弱，但深入挑战有一定完成 | 不同参与深度可能并存 | 聚合数据不能识别具体普通/硬核人群 |
| 收集成就较普及，但时长不高 | 收集容易、顺路或目标较浅 | 成就设计与类别构成，不能直接解释为探索吸引力强 |

重点可以检验“开放世界等标签是否更常伴随主线较浅、可选参与较高的组合”。先做代表游戏对照、散点图、标签组内分布与Spearman相关；条件允许再作简单回归，不为首版强制引入高级模型。

统计单位始终是游戏，避免把同一游戏的几十项成就当作几十个独立游戏样本。固定标签归一化规则、指标和过滤条件；关注标签共现、发售年份、类型、热度、内容长度与观察机会。区分全局解锁率和经核验的条件比例，报告覆盖与样本数；小试点以描述和口径验证为主，不据两款游戏推断整个市场。

## 分阶段实施顺序与验收

| 阶段 | 工作与产物 | 完成标准 |
|---|---|---|
| 1：两款FF7语义试点 | 固定规则说明；完整成就清单初标；审核主线、路线及典型辅助目标 | 内容类型、困难模式和INTERmission分开；每个发布节点及关系有证据；未知有原因 |
| 2：本地输入与数据契约 | 确定标签/RAWG/目标强度补充结构；实现只读提取与SQLite导入 | 选样、计数、来源时间、空值、键、指纹可核对；没有远端写入；重复运行不覆盖快照 |
| 3：初标与人工修订 | 规则baseline；需要时再评估模型辅助；按游戏复核 | 建立人工参考集，记录修订、争议和覆盖；自动结果仍为suggested；无准确率证据不声称准确 |
| 4：20～30款试点 | 按主线清晰、有效展示名、标签覆盖选样，并兼顾不同类型 | 排除原因可追溯；每款主线关键节点复核；辅助指标满足审核与接触条件；报告样本偏差 |
| 5：指标和可视化 | 版本化主线漏斗、辅助参与画像、标签对比、RAWG子样本时长对照 | 公式条件检查通过；未定义与0分开；图表只显示display_name；结论有局限与替代解释 |
| 6：质量允许后扩展 | 向plan.md的100～1000款目标逐步扩展 | 扩展前检查人工质量、类别可比性与覆盖，不一次全量复制或全站抓取 |

正式样本按项目既定年份范围筛选；核验数据库中的实际发行信息，排除无法确认范围的游戏。来源演示页面不自动纳入样本。随机选样时固定random_state=42并保存清单；人工挑选试点要说明便利样本偏差。少量游戏没有某类目标时保持缺口，不为了凑齐画像而猜测类型。

计划文件分工（以下程序尚未创建，不生成空占位文件）：

- import_snapshot.py：样本清单、远端只读提取、源字段/时间校验、本地快照与质量台账。
- classify.py：基于展示名和条件文本初标，记录方法、输入指纹与版本；规则对照先行，percent不用于决定语义类型。
- review.py：人工修订、目标强度与主线路线/关系核验；初版可用本地审核文件，不先建设复杂界面。
- analyze.py：验证公式前提、按游戏汇总、标签比较、时长补充分析与图表。

具体表与字段先按[database规划](../database/README.md)确认。不存在的程序不列为现有可运行命令，现有schema测试也不代表未来补充结构已验证。

## 执行、恢复与发布规则

1. 提取前实时检查mapping_issues未解决记录；使用短时、强制只读的一致性事务。游戏、成就、标签分别读取，避免一对多联接重复成就；不调用共享建表、队列、配额或修复写入逻辑。
2. 来源抓取时间与本地提取时间分别记录；同一读取事务不意味着各源同期采集。发布时绑定dataset_version、annotation_version、标签版本、样本和分析参数。
3. 每项标注元数据与类型在同一短事务落库；模型/网络请求在事务外执行。本地单写入者，重跑按版本和身份键续接，人工approved结果不被自动结果覆盖。
4. 程序失败记录为失败/待处理，证据不足记录为uncertain；不把网络失败当“无数据”或最终unknown。发布后的标注版本按不可变成果使用，变更生成新版本。
5. 主线关系检查同版本、同游戏/路线、审核状态、顺序、无环、必然前置和正分母。辅助目标条件比例需同等核验；不满足时仍可报告原始单项率并说明限制。
6. 输出数据字典、样本/覆盖表、审核与排除台账、图表、方法与局限。原始副本、运行日志和临时报告放database/data或process/runtime并保持Git忽略；可提交的代码/规划与原始数据分开。

## 外部网站接入决策

首版使用已有共享数据与本地标注，外部网站不是完成漏斗分析的必要前提。已有公开API的字段和授权范围单独核验；不把本地推断称为站方分类，也不因一次请求成功就推定全量额度。

2026-10-14对[Gamer Guides示例页](https://www.gamerguides.com/resident-evil-requiem/steam-achievements/overview)的少量核验确认Time/Difficulty在初始HTML中，可按下面的语义选择器解析；这只是单页格式证据，未验证全站覆盖：

```css
.achv-roadmap-chip[title="Time"] .achv-roadmap-chip-value
.achv-roadmap-chip[title="Difficulty"] .achv-roadmap-chip-value
```

作者、评分方法、是否指全成就、平台和DLC范围仍需核验。[使用条款](https://www.gamerguides.com/terms)第3/5节要求系统采集与数据集用途获得事先书面许可；更换HTML/API/手工系统摘录不自动解决授权。本次少量请求返回200且经过Cloudflare，不代表已获授权或批量不会被限流，实际阈值未知。

若取得许可或获准导出，再实现独立可选适配器：明确URL与appid匹配、字段缺失、范围、来源日期、许可要求及约定访问频率。遇403挑战/429限流挂起来源，记录原因，不进行绕过或快速重试；按约定避免重复访问。它输出“攻略估计”字段，不覆盖RAWG实际时长，也不阻塞主流程。

## 下一轮最小可验收任务

先整理两款FF7的标注规则与人工审核清单：确认普通主线、困难挑战、INTERmission路线，选择可代表接触和深入完成的辅助目标，列出未知及证据缺口。随后确定本地特征快照契约并实现导入，做出首份可追溯的漏斗与参与画像。扩样、模型辅助和外部攻略批量数据均按后续阶段推进。
